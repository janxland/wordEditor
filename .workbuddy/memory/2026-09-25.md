## 部署评估：api-node 上 ROGINX 服务器（103.52.153.223 / c202608060983447）

用户问「部署到 ROGINX 会不会撑开内存和性能」。结论：**默认配置会撞车，限流后可用**。

### 服务器实测水位（tailscale ssh 取的，非文档推算）
- 内存 **3915MB 总 / 2159 已用 / 可用 1756MB**，swap 2047MB 里**已用 910MB（44%）**
- 4 vCPU Xeon 8272CL @2.6GHz，load 0.17（闲置）；cgroup v2；磁盘 39G 用 22G，**剩 18G**
- 容器实占合计 ~916MB（ablaze 376M 最大）；8787/8788 端口空闲

### wordEditor 实测开销（Python RUSAGE_CHILDREN 量 pandoc 子进程峰值）
- **pandoc 单进程峰值 RSS：1KB 小稿 279MB / 40KB 真实论文 427MB**
- 4 路并发合计 **1708MB**（≈1.67GB）
- 单次构建墙钟 ~2.2s（md→html 1.5s + html→docx 0.7s）+ Node 后处理
- api-node 空载 RSS **98MB**；单请求 96MB body 解析后 RSS 增量 **219MB**（base64 膨胀 2.3 倍）
- 入库体积仅 10MB（.tools/.git/node_modules/.cache 都不入库）

### 撞车根因（关键，务必记住）
- `jobs/gate.ts` 的 `defaultConcurrency()` = `floor(totalmem × 0.5 / 400MB)`，上限 8
  → 这台机器算出 **4 路**。4 × 427MB = 1708MB，**等于全部可用内存 1756MB**。
- **Node 的 `os.totalmem()` 读宿主 sysinfo，不感知 cgroup 限额** —— 即便给容器加
  `--memory 512m`，它仍然算 4 路，只会在容器内被 OOM kill。
- **OOM 连坐**：本机 oom_score_adj 是 alist +500 / bi-tracker +300 / ncm +200 / 其余负值。
  新进程默认 0 → 内存告急时内核**先杀 alist、bi-tracker、ncm，最后才杀 wordEditor**。
  也就是它不会先死，会先拖死邻居。
- swap 已用 44%，再压 1.7GB 会进 swap → pandoc 堆是随机访问，换页后构建慢 10 倍以上。

### 部署阻塞项（部署前必须处理）
1. **pandoc 二进制跑不了**：`.tools/pandoc-3.9-arm64/bin/pandoc` 是 **Mach-O（macOS）**，
   且 `.tools/` 在 gitignore 里不入库 → 镜像里必须自己装 Linux pandoc。
2. **版本必须钉 3.10.2**：本机实际命中 `/Users/Admin1/homebrew/bin/pandoc` = **3.10.2**（不是 3.9）。
   Ubuntu 24.04 apt 装的是 3.1.11，会导致 docProps/custom.xml 的 generator 与本地产物分叉。
3. **没有 Dockerfile**，`services/api-node/` 下只有 src/dist/package.json。
4. **安全**：`main.ts` 绑 `0.0.0.0`、bodyLimit 96MB、无任何鉴权/限流
   → 公网暴露等于「一次 POST 换一个 427MB 进程」的免费 DoS。
5. **`dist/` 仍是旧的**，打包前必须重新 build。

### 推荐上线配置（若要部署）
- `WORDEDITOR_MAX_CONCURRENCY=1`（强制 1 路，别让闸门自算）
- 容器 `--memory 768m --memory-swap 768m --cpus 1.0`（不给 swap，宁可自杀不要换页）
- **oom_score_adj 设 +600**（比 alist 的 +500 还高）→ 真 OOM 时它先死，保护邻居
- 只绑 `127.0.0.1` + nginx 反代；nginx 侧 `client_max_body_size 20m` + `limit_req`
- **SSE 必须关缓冲**：`proxy_buffering off` + `proxy_read_timeout 300s`
  （server.ts 注释：Node 的 requestTimeout 实测 5s 就会掐断 SSE，他们故意没设）
- pandoc 钉 3.10.2（下 GitHub release tarball，不要 apt）
- 镜像 ~350-450MB，磁盘 18G 够；`.cache` 有 6h TTL + 15min 巡检，建议挂卷

## 管线开销归因：内存/时间/体积到底花在哪（实测）

用户追问「为什么用这么多内存，还有别的优化方案吗」→ 做了完整归因实验。
报告：`.cache/regression/PANDOC-COST-ANALYSIS-2026-09-25.md`
脚本：`/tmp/measure.py`（RUSAGE_CHILDREN 量峰值）、`/tmp/clean-ref.py`（剥模板垃圾）、
`/tmp/ab-ref.sh`（A/B）、`/tmp/breakdown.mjs`（拆部件）、`/tmp/refdoc-audit.mjs`（模板体检）、
`/tmp/real-pipeline-image.mjs`（真实 HTTP 管线带图构建）

### 结论：内存主因是 `--embed-resources`，不是 pandoc 天生吃内存、也不是模板大
输入 `input/储油罐变位罐容校准.md`（22KB + 9 图 / 272KB）：

| 阶段 | 当前 | 去 embed | 变化 |
| :-- | --: | --: | :-- |
| 段1 md→html 峰值/墙钟 | 127MB / **2089ms** | 110MB / **186ms** | 墙钟 −91% |
| 段1 输出中间 HTML | **1368KB** | **55.5KB** | −96% |
| 段2 html→docx 峰值 | **365MB** | **129MB** | −65% |
| 两段合计峰值 | 492MB | 239MB | −51% |

- 中间 HTML 多出来的 1312KB 里 **997KB 是 `--mathjax` 塞进来的整行 MathJax JS**
  （html→docx 阶段根本不执行 JS，纯浪费）。
- **段2 内存几乎只由输入 HTML 体积决定，与模板大小无关**（129/127/129MB 三档持平）。
- 模板垃圾**吃时间不吃内存**：段2 墙钟 821ms → 385ms（剥 div/rsid）→ 230ms（再删孤儿图）。

### 体积归因：真实产物 941KB 里 659KB 是模板孤儿图
- `templates/hutb-shared/reference.docx` 自带 6 张图（image1–6，含 image5.png **301.8KB**），
  而模板自己的 `document.xml` 只有 1KB、**零引用**；pandoc 用 `--reference-doc` 会原样复制 media。
- 另有 `webSettings.xml` 里 **951 个 `<w:div>`**（381KB）+ `settings.xml` 里 **2974 个 `<w:rsid>`**（81KB）
  —— Word 编辑历史 / 网页粘贴残留。
- 污染模板：`hutb-shared`（6 个模板共用！）、`hutb-guanke-xuenian`、`hutb-gongke-fengmian`；
  `apa7` 干净（脚本生成，36.7KB，div=0 rsid=9）。
- **清理后：产物 941KB → 292KB（−69%）**；`document.xml`/`styles.xml`/9 张文档图**逐字节一致**（零侵占已验证）。

### 顺带查出 3 个真 bug
1. **产物不可复现 + 泄漏绝对路径**（最严重）：连续两次构建，`document.xml` 的
   `pic:cNvPr@descr` 分别是 `.cache/wordeditor-api-node/f3a16fb7-…/` 和 `…/d90bf508-…/`。
   根因 = `--embed-resources` + `normalizeStandaloneHtml` 把 data URI 换回**任务目录绝对路径**。
   注意：pandoc 在图片**无 alt** 时用 `src` 填 `descr` → embed 时一个 descr 吃掉 339KB base64。
2. 模板携带 659KB 孤儿图 + 460KB 元数据垃圾（见上）。
3. `--mathjax` 在 docx 管线是纯浪费（塞 997KB JS，段2 不执行）。

### 优化方案（收益/风险）
| # | 方案 | 收益 | 风险 | 验证 |
| :-: | :-- | :-- | :-- | :-- |
| 1 | 清理 3 个 reference.docx（剥 divs、rsid、孤儿 media） | 段2 −72% 耗时、产物 −69% | 零 | ✅ 逐部件已验证 |
| 2 | 段1 去 `--embed-resources`，删 `normalizeStandaloneHtml` | 段1 −91% 耗时、段2 −65% 内存、产物可复现 | 低 | ✅ descr 归一后 document.xml 全等 |
| 3 | 段1 去 `--mathjax` | 中间 HTML −96% | 低 | ⚠️ 公式未验证 |
| 4 | 两段合并单段 | 省一个 pandoc 进程 | **中** | ❌ 会丢 HTML class→custom-style 映射，**不建议** |

**组合 1+2+3 后单篇峰值 492MB → 239MB**，ROGINX 上并发可从 1 路提到 2–3 路。

## 第三次返工：封面/评分表改「字节级整页搬运」+ 修好 Node 引擎缺注入的真 bug

### A. 方法换了：从 lxml 解析-序列化 → 字节级原样切片 + 字符串插入

旧做法（错）：`etree.fromstring` 解析源 docx → deepcopy 元素 → `etree.tostring` 写块
→ 注入时再解析整份 document.xml 插元素 → 全量序列化。这是"重排版"不是"搬运"。
具体损失（已实测举证）：
1. `nsmap` 只从 `elements[0].nsmap` 取 → 首元素没用到的前缀后续元素用了就丢声明
2. 顶层 `bookmarkEnd` 被删、段内 `bookmarkStart` 保留 → **书签不闭合**（源 idx5 start /
   idx6 end，切片 [0,8) 两个都在）→ Word 报"内容有问题"
3. 丢 `w:proofErr`、注释、PI；属性顺序与空白被重写

新做法：
- `template_factory.slice_block()` 改为字节级：新增 `iter_body_top_level(raw)` 扫描器

  最后在 `<w:body>` 后 / `</w:body>` 前**字符串插入**，产物 document.xml 除插入点外零改动。
- 序列口径统一：`iter_body_top_level` 与 `detect_blocks` 都是"body 顶层元素"序列

## 第四次返工：封面"渲染不一致" + 日文字体 —— 根因都在 reference.docx 的文档级默认值

用户第三次否决："封面完全没有完全一致""多级列表怎么会使用日文字体"。两个都是真 bug，
且**都不是块（block）的问题**——块的字节早就 100% 一致了。

### 根因 A：从零造 reference.docx，把文档级默认值换掉了

`build_reference()` 用 python-docx 的**默认模板**从零生成，于是：
- `docDefaults.pPrDefault` 被塞了 `<w:spacing w:after="200" w:line="276" w:lineRule="auto"/>`
  → 源 docx 是**空** `<w:pPrDefault/>`。封面/评分表里没写死 spacing 的段落全被套上
  1.15 倍行距 + 段后 200 → 整页被撑开。
- `docDefaults.rPrDefault` 写 `w:eastAsiaTheme="minorEastAsia"`，而 theme 的 minorFont
  没定义 `ea` → 解析后落到 fallback。
- `settings.xml` 的 `<w:themeFontLang w:eastAsia="ja-JP"/>`（python-docx 默认模板自带，
  源 docx 是 **zh-CN**）→ **默认东亚字体被解析成日文字体**，多级列表编号
  「一、（一）、①」跟着吃默认 → 用户看到日文字体。
- `docDefaults` 的 `<w:lang w:eastAsia="en-US">`（源是 zh-CN）、theme major/minor 互换。

**修法（方法论级）**：不再逐参数对齐（永远对不齐），改成 **reference.docx 整包克隆源 docx**：
- `template_factory.build_reference_cloned()`：复制源 docx 全部部件 → 清空 body 只留 sectPr
  （页面设置沿用源）→ 往 `</w:styles>` 前**追加**源没有的样式 → settings 兜底把
  `themeFontLang` 的 ja-JP 改 zh-CN → 源无 numbering 时补一份并注册 Content-Type/rels
  → 删掉孤儿 media 及其 rels。
- `build()` 默认 `reference.mode=clone_source`（有 source.docx 时）；`from_scratch` 可退回。

### 根因 B：克隆后 pandoc 找不到 heading 样式

追加样式后 pandoc 输出了 `Heading1`/`Heading2`，而产物 styles.xml 里没有这两个 styleId
→ 段落引用悬空、DSL 的 `id: "1"/"2"` 全落空。**pandoc 按 `"Heading 1"`（首字母大写）
查样式名**，python-docx 写的是小写 `heading 1`。工厂追加时把 name 改写成大写即可，
改完 pandoc 输出回到 `1`/`2`。
另：`basedOn/next="Normal"` 在源里断链（源默认段落 styleId 是 `a`），需重指。

### 验收口径升级（这才是"复制粘贴"的判据）

只比字节不够——字节一致只能证明没被改写，证明不了渲染一样。新增**解析后格式**比对：
`template_verify.py` 加 `style_index()` / `resolve_para()`，把
docDefaults → pStyle/basedOn 链 → 段落自身 → 首个 run 全解析，逐段比
jc/spacing/ind/fonts/sz/b/lang_ea；再加"东亚语言必须 zh-CN"。
**反向验证**：退回 from_scratch reference → 立刻 FAIL：cover 20 段 + tail 74 段全不同
（差异正是 after=200/line=276/auto 与 lang_ea=en-US）+ themeFontLang=ja-JP。
说明这项检查不是橡皮图章。

### 顺带修完的：英文摘要按模板要求落位（ABSTRACT 四号 TNR）

模板明写 `[ABSTRACT] …（四号 Times New Roman）`，但两层把它压成"文章的正文"：
1. lua `zhengwen-style.lua` 写死 `wrap('文章的正文')`；
2. Python/Node 的 `apply_abstract_styles` 默认参数 `en_abstract*_style_id="ae"`。
改法（双侧对称，做成通用能力不是 hack）：

  之后 → 只能在 `Blocks` 里改 Div 的 custom-style，`Para` 钩子拿不到已包装的段落）。

  加 `ABSTRACT_STYLE_KEYS` 并从 dsl 读；Node `styles-dsl.ts` 加 `abstract?: Record<string,string>`
  + `abstractStyleIds()` 把 snake_case 转 camelCase 传给 `applyAbstractStyles`。
  **只改 lua 不改 DSL 会被后处理覆盖回去**（实测：改完 lua 段落仍走"文章的正文"）。
- `AbstractTitle` 的 name 必须是 `AbstractTitle`（无空格）——pandoc 拿 custom-style 值

- 摘要标题字号同时修正 36→28、对齐 center→both（源 docx 实测：题目才 36/center，
  摘要/关键词/ABSTRACT/KEY WORDS 一律 sz=28 且无 jc）。
