## 修复：代码附录被压成一整段（pipeline 真实 bug，已在源码修掉）

用户反馈"代码布局太乱、要求有换行"。排查结果：

- **现象**：`基于多模型对比的泰坦尼克号乘客生存预测研究.docx` 里 701 行代码挤成 **1 个段落**，全文 `<w:br/>` 数量为 **0**（正确应为 701 行 → 720 个 br，含空行）。
- **定位过程**：pandoc 本身正确（合成 700 行 fenced block 经同链路 br=699；真实 MD 手工走 html→docx br=720）→ 用 `pipeline/build.py --no-postprocess` 得到 br=720 → 逐层加后处理，**`postprocess_document.py` 一步把 720 个 br 全部清零**。
- **根因**：`_patch_paragraph_refs` 对含 `[` 的段落做引用改写，流程是「`paragraph_plain_text()` 取纯文本 → `rebuild_paragraph_content()` 清空全部子元素 → 按纯文本重排 run」。而 `paragraph_plain_text` 只收集 `<w:t>`，**`<w:br/>` / `<w:tab/>` 不在其内**。pandoc 把整个代码块写成**一个** `SourceCode` 段落、换行靠段内 `<w:br/>` 承载，于是代码里任何 `[0]`/`[1]`/`[2]`… 下标只要命中文献表书签 `Ref1`/`Ref2`…，整段就被重建，格式尽失。旧稿里还因此生成了 43 个**代码内部的伪 REF 域**（总域数 49）。
- **修复**（两文件，最小 diff）：
  - `pipeline/postprocess_document.py`：新增 `_is_verbatim_paragraph()` —— `w:pStyle ∈ {SourceCode, VerbatimChar}` 或段内含 `w:br`/`w:tab` 即跳过；在 `apply_headings` 与 `_patch_paragraph_refs` 两处入口判定，这类段落一律保持原样。
  - 顺带把 `REF_IN_TEXT` 从 `\[(\d+)\]` 放宽为 `\[(\d+(?:\s*,\s*\d+)*)\]`，支持 `[7,8,9,10]` 逗号组；`ooxml_util.append_ref_field` 增加 `wrap: bool = True` 参数（组内编号只显示本体，方括号/逗号作为上标文本 run 补齐）；组内任一编号不在文献表时整组保持原样。
- **验证**：重导出后 全文 br=720、代码段 br=720（逐行换行恢复）；REF 域 15 个、编号 1–15（此前只有 1–6，且混入 43 个伪域）；`[7,8,9,10]` / `[11,12,13,14,15]` 已变上标；图 15 / 表 2 / 图号 15 / 表号 2 未受影响。
- **沉淀**：`hutb-docx-export` SKILL.md 新增「代码附录必须校验 `<w:br/>` 数量」已知坑 + 自检口径（br ≈ 代码行数−1；SourceCode 段内不应出现 REF 域）。
