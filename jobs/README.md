# jobs/ · 接单区（**不是代码区**）

> 一句话：**客户的东西放这里，代码的东西放别处。这个目录不进 git。**

## 为什么单独开一个目录

之前接单稿件直接堆在 `input/`，结果是：

- 工作区**永远脏** —— `git status` 一打开就是几十兆的客户文件，
  代码评审 / 去冗余扫描 / diff 全被淹没（第 03 轮就差点被误判成"未接线模块"）。
- 仓库体积失控 —— 两单稿件 7.5M + 34M 直接躺在仓库根目录。
- 客户稿件进版本库有**隐私与版权风险**，交付完也不该留痕。

所以：`jobs/` 是接单业务的唯一工作区，`.gitignore` 里整目录忽略。

## 目录规约

| 目录 | 放什么 | 什么时候动 |
|---|---|---|
| `jobs/inbox/` | 客户刚发来的原始来稿（md / docx / 图片 / 素材），**未开工** | 接到单先落这里，不改内容 |
| `jobs/work/` | **在建**的工作区 —— `we build` 直接指向这里的目录 | 开工时从 inbox 复制过来；产物 docx 回写到同级 |
| `jobs/done/` | 已交付的成品与源文件，留底备查 | 交付后从 work 挪过来；超过保留期可自行清理 |

**工作区约定不变**：工作区 = 输入 Markdown 所在的目录，`we build` 默认把 docx
回写到该目录。所以一单 = `jobs/work/<单号-标题>/` 一个目录，md 与图片都放里面。

## 怎么用 CLI

```bash
# 1. 客户来稿落 inbox
cp ~/Downloads/某论文.md jobs/inbox/          # 或整目录

# 2. 开工：复制到 work，一单一目录
mkdir -p jobs/work/2026-10-04-某论文
cp jobs/inbox/某论文.md jobs/work/2026-10-04-某论文/

# 3. 构建（产物回写到该工作区）
we build jobs/work/2026-10-04-某论文 -t hutb-guanke

# 4. 交付后归档
mv jobs/work/2026-10-04-某论文 jobs/done/
```

CLI / MCP 的接单提醒：`we build` 若传入 `jobs/**` 路径，会在 stderr 打一行提示
说明产物回写到工作区；MCP 的 `build_docx` 同样以「md 所在目录」为工作区。

## 什么**不要**放这里

- ❌ **代码自带的样例输入** —— 那是 `input/` 的事，要入库（E6 回归用的就是
  `input/暑假社会调查报告-样例.md`）。
- ❌ 模板、`spec.yaml`、`styles.yaml`、`reference.docx` —— 在 `templates/`。
- ❌ 任何需要长期版本管理的东西 —— 这里整目录不入库，丢了没法恢复。

## 关于 `input/`（容易搞混）

`input/` 是**代码的样例与回归输入**，本来就**要入库**。两者的分界：

| | `input/` | `jobs/` |
|---|---|---|
| 内容 | 模板样例、回归测试用 md、随库图片 | 客户稿件、交付物 |
| 是否入库 | ✅ 是 | ❌ 否（整目录 ignore） |
| 能否删 | 不能（E6 产物等价回归依赖它） | 随时可清 |

**判断口诀**：「删掉会不会影响别人跑通这个项目」—— 会 → `input/`；不会 → `jobs/`。
